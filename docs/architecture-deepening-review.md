# Architecture Deepening Review

**Review date:** 2026-09-27  
**Scope:** Assessment of the supplied *Architecture Review — Deepening Opportunities* report against the current source, architecture notes, system requirements, and course delivery criteria. This is an architecture assessment and documentation record; no runtime code was changed and no tests were run for this review.

## Decision summary

The external report correctly identifies the orchestrator as the strongest future deepening candidate, and it is right to ask for a shared domain vocabulary. The evidence supports a *bounded exploratory refactor*, not an immediate submission requirement. Keep the working end-to-end system stable through hosted acceptance and course-grader access gates first. If the project continues after those gates, deepen orchestration behind its existing `MSAIEOrchestrator.handle(message, confirm_action) -> AgentResult` boundary, preserving centralized safety ordering and trace semantics.

The report's claim that a new `CONTEXT.md` is a prerequisite is too strong: the repo already has an SRS, architecture contract, traceability matrix, security control map, ADRs, and typed `AgentResult` boundary. A concise domain glossary could improve consistency, but it should be derived from those artifacts and only introduce typed facts where a concrete interface benefits. The report also says “4 Deepening Candidates” while presenting five candidates including the domain model, calls orchestrator churn “highest” without recent file-history evidence, and its generated HTML visibly contains a Mermaid syntax error in the proposed vocabulary diagram. Treat the report as useful design input rather than a validated architectural verdict.

## Architecture and framework decision against the project prompt

The supplied project prompt explicitly permits the web app, orchestrator, RAG index, and MCP server to run inside one free-tier service, and its rubric asks for clear component separation rather than separate deployments. Keep the current **single-service modular monolith**: retain distinct FastAPI, orchestrator, MCP client/server, RAG, provider, and synthetic-data modules; do not split them into microservices absent a demonstrated scale, ownership, or fault-isolation need. This is not an endorsement of one undifferentiated module.

The prompt also asks the design documentation to justify a framework or manual orchestration approach. Keep the deterministic, manually controlled orchestrator for this bounded HR workflow. It explicitly selects tools, sequences multi-step cases, applies privacy and confirmation rules before actions, and leaves the LLM with answer composition. This is a defensible agentic design: the required behaviors are visible and testable, and a model cannot improvise tool use or approve an action. Document that choice directly in the design rationale and demo narrative.

Do **not** add LangChain solely to make the project look more agentic or modern. Its current documentation presents LangChain as a prebuilt agent loop/integration layer and LangGraph as a more customizable orchestration runtime; neither is required by this rubric, which accepts manual orchestration. Adding either now would introduce a new runtime abstraction and migration/evaluation work without closing the hosted-answer or grader-access gates. Reconsider LangGraph only if the product gains durable multi-turn state, resumable human approval, branching/parallel workflows, or replay requirements that the existing explicit state flow cannot support. A thin deterministic orchestrator extraction is a simpler response to the current maintainability concern. See the [LangChain agent documentation](https://docs.langchain.com/oss/python/learn) and [LangGraph reference overview](https://reference.langchain.com/).

The prompt does require cold-start behavior to be explained and asks for p50/p95 across representative tasks, with cold and warm separated where possible. Preserve the measured local latency distributions and the single hosted wake-to-ready observation as different scopes; in the presentation explain that the 33.466-second hosted sample measures wake-to-ready only, not cold-start-to-live-model completion. Do not imply a reliable hosted latency distribution from that one sample.

## How to judge a future deepening

Use the codebase-design criteria rather than module length alone:

1. Name a real change scenario (for example, adding a PTO rule without changing remote-work behavior).
2. Identify which decisions and invariants change, which callers need to know them, and how far the change currently propagates.
3. State the smallest stable interface that protects the invariant and gives the caller leverage.
4. Apply the deletion test: removing the proposed wrapper/handler/module should remove meaningful complexity, not just move imports and forwarding calls.
5. Verify through the public chat or `RagIndex` contract with the appropriate existing evaluation; preserve citations, safety outcome, MCP call order, and trace content.

Do not create one handler protocol per branch by default. Use typed facts when the types prevent a real class of invalid state or make the model/validator contract safer; otherwise the type layer may simply mirror current dictionaries.
